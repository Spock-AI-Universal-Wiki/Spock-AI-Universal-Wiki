    WarpCore db

    Purpose¶

    WarpCore/db.py is a shared SQLite helper layer for Spock V2. It exists to give the GUI, wiki_agent daemon, extractor, RAG API server, MCP server, and CLI maintenance scripts one dependency-light way to open databases, apply schema DDL, inspect tables, and manage sqlite-vec vector indexes without importing PyQt or app-specific services.

    It standardizes low-level connection behavior — WAL mode, busy timeout, foreign keys, and opportunistic query-planner refresh — and isolates the optional sqlite_vec extension behind a safe loader. This lets callers use vector search when the extension is available and degrade gracefully when it is not.

    Structure¶

    The module is flat and function-oriented; it defines no classes. It begins with a module docstring and imports, then defines module-level constants:

    • DEFAULT_SHIPS_DB = "ship_computer.db"
    • DEFAULT_UIEG_DB = "uieg_capture.db"
    • _SQLITE_VEC_AVAILABLE, set by the guarded sqlite_vec import
    • _VEC_TABLE_NAME = "documents_vec"

    The functions are organized into three practical groups:

    1. Path, connection, and schema bootstrap
    2. resolve_db_path(path, name) — WarpCore/db.py:30-34
    3. connect(db_path, timeout) — WarpCore/db.py:37-47
    4. ensure_schema(db_path, schema_sql) — WarpCore/db.py:50-57

    5. _load_sqlite_vec(conn) — private helper shown in the excerpt, used by connect() and vector-table maintenance

    6. sqlite-vec introspection and maintenance

    7. vec_table_exists(conn) — WarpCore/db.py:81-89
    8. vec_table_names(conn) — WarpCore/db.py:92-100
    9. vec_shadow_names(conn, name) — WarpCore/db.py:103-112
    10. drop_vec_table(conn, name) — WarpCore/db.py:115-150
    11. delete_documents_vec(conn, doc_ids) — WarpCore/db.py:153-173
    12. ensure_documents_vec(conn, dim) — WarpCore/db.py:176-191
    13. rebuild_documents_vec(conn) — WarpCore/db.py:209-244

    14. upsert_documents_vec(conn, doc_ids) — WarpCore/db.py:247-282

    15. Generic SQLite table utilities

    16. table_exists(db_path, table) — WarpCore/db.py:285-294
    17. row_count(db_path, table) — WarpCore/db.py:297-303
    18. table_names(db_path) — WarpCore/db.py:306-316

    The public API is mostly small functions that take either a db_path string or an open sqlite3.Connection. Path-based helpers open and close their own connections, while connection-based helpers assume the caller owns the connection lifecycle. Some helpers, such as ensure_schema() and drop_vec_table(), commit internally; others leave transaction control to the caller. The optional sqlite_vec dependency is guarded by _SQLITE_VEC_AVAILABLE and _load_sqlite_vec(), allowing the module to import and operate in non-vector environments.

    Purpose¶

    WarpCore/db.py is a shared SQLite helper module for Spock V2. Its main job is to provide a small, reusable database layer for local Spock data, with special focus on maintaining a sqlite_vec vector index for document embeddings.

    The module exists so that other parts of the application do not need to repeat low-level SQLite logic such as:

    • opening connections consistently,
    • checking whether tables exist,
    • creating or dropping the vector index,
    • syncing embedded documents into the vector table,
    • deleting stale vector rows,
    • rebuilding the vector index from the source documents table.

    It is a utility module, not an application entry point. It is intended to be imported and called by higher-level Spock services.

    Structure¶

    The module is organized as a flat collection of functions. There are no classes in the visible structure.

    Connection and schema helpers¶

    • resolve_db_path(path, name) — WarpCore/db.py:30-34
      Resolves a database path, likely using os and pathlib.

    • connect(db_path, timeout) — WarpCore/db.py:37-47
      Creates and returns a SQLite connection.

    • ensure_schema(db_path, schema_sql) — WarpCore/db.py:50-57
      Schema bootstrap helper. It is positioned as the step that makes sure the expected SQLite schema exists.

    Vector-table introspection helpers¶

    • vec_table_exists(conn) — WarpCore/db.py:81-89
      Checks whether the vector table is present.

    • vec_table_names(conn) — WarpCore/db.py:92-100
      Lists vector-related tables.

    • vec_shadow_names(conn, name) — WarpCore/db.py:103-112
      Resolves auxiliary or shadow tables associated with a sqlite_vec table.

    Vector-table lifecycle helpers¶

    • drop_vec_table(conn, name) — WarpCore/db.py:115-150
      Drops the vector table and is the natural place where sqlite_vec shadow tables are cleaned up.

    • delete_documents_vec(conn, doc_ids) — WarpCore/db.py:153-173
      Removes specific document IDs from the vector index.

    • ensure_documents_vec(conn, dim) — WarpCore/db.py:176-191
      Creates the vector table if it is missing and a valid embedding dimension can be determined.

    • rebuild_documents_vec(conn) — WarpCore/db.py:209-244
      Rebuilds the vector index from the documents table.

    • upsert_documents_vec(conn, doc_ids) — WarpCore/db.py:247-282
      Syncs a specific set of documents into the vector index without rebuilding the whole table.

    Generic table helpers¶

    • table_exists(db_path, table) — WarpCore/db.py:285-294
      Checks whether a named table exists.

    • row_count(db_path, table) — WarpCore/db.py:297-303
      Returns the number of rows in a table.

    • table_names(db_path) — WarpCore/db.py:306-316
      Returns the list of table names in the database.

    Private helpers visible in the excerpt¶

    The excerpt also shows private helpers that support the vector logic:

    • _load_sqlite_vec(conn)
      Loads the sqlite_vec extension into the connection.

    • _infer_embedding_dim(conn)
      Infers the embedding dimension from existing documents.embedding values.

    • _SQLITE_VEC_AVAILABLE
      Module-level flag indicating whether the sqlite_vec extension is usable.

    • _VEC_TABLE_NAME
      The name of the vector table, used throughout the vector helpers.

    Control flow¶

    The module has no top-level execution. Control flow begins when another part of Spock calls one of its functions.

    Vector deletion flow¶

    delete_documents_vec(conn, doc_ids) — WarpCore/db.py:153-173

    1. If sqlite_vec is unavailable, return 0.
    2. Load the sqlite_vec extension.
    3. If the vector table does not exist, return 0.
    4. Split doc_ids into chunks of 500.
    5. For each chunk:
    6. Build an IN (?, ?, ...) clause.
    7. Execute DELETE FROM <vec_table> WHERE doc_id IN (...).
    8. Add the chunk size to the returned count.
    9. Ignore sqlite3.Error for that chunk and continue.
    10. Return the accumulated count.

    This flow is intentionally defensive: a failure in one chunk does not stop processing of the remaining chunks.

    Vector table creation flow¶

    ensure_documents_vec(conn, dim) — WarpCore/db.py:176-191

    1. If sqlite_vec is unavailable, return.
    2. If the vector table already exists, do nothing.
    3. If dim is not supplied, infer it from the documents table.
    4. If the inferred dimension is missing or non-positive, return.
    5. Create the virtual table:
    6. CREATE VIRTUAL TABLE IF NOT EXISTS <vec_table> USING vec0(doc_id INTEGER PRIMARY KEY, embedding float[<dim>])
    7. Commit.
    8. Swallow exceptions and return.

    This function is a lazy initializer. It does not populate the table; it only makes sure the table exists with a valid dimension.

    Full rebuild flow¶

    rebuild_documents_vec(conn) — WarpCore/db.py:209-244

    1. If sqlite_vec is unavailable, return 0.
    2. Infer the embedding dimension from documents.
    3. If no valid dimension is found:
    4. Drop the vector table.
    5. Return 0.
    6. Drop the existing vector table.
    7. Create a fresh vector table with the inferred dimension.
    8. Read all rows from documents where:
    9. embedding IS NOT NULL
    10. length(embedding) > 0
    11. For each row:
    12. Unpack the embedding BLOB as little-endian float32 values.
    13. Serialize the floats using sqlite_vec.serialize_float32.
    14. Insert into the vector table.
    15. Count successful inserts.
    16. Commit.
    17. Return the number of inserted vectors.
    18. If an outer exception occurs, return 0.

    This is the most destructive vector operation in the module. It replaces the vector index entirely.

    Targeted upsert flow¶

    upsert_documents_vec(conn, doc_ids) — WarpCore/db.py:247-282

    1. If sqlite_vec is unavailable or doc_ids is empty, return 0.
    2. Load the sqlite_vec extension.
    3. Ensure the vector table exists.
    4. If the vector table still does not exist, return 0.
    5. Select the requested documents from documents where:
    6. id IN (...)
    7. embedding IS NOT NULL
    8. length(embedding) > 0
    9. For each selected document:
    10. Unpack the embedding BLOB as float32 values.
    11. Delete any existing vector row for that doc_id.
    12. Insert the new vector row.
    13. Count successful updates.
    14. Return the number of updated documents.
    15. If an outer exception occurs, return 0.

    This is the incremental path. It is cheaper than a full rebuild when only a few documents changed.

    Generic table helper flow¶

    The generic helpers follow a simple open-use-close pattern:

    • table_exists(db_path, table) — WarpCore/db.py:285-294
    • Open a connection.
    • Query sqlite_master.
    • Return whether the table name was found.

    • Close the connection.

    • row_count(db_path, table) — WarpCore/db.py:297-303

    • Open a connection.
    • Run SELECT COUNT(*) FROM "<table>".
    • Return the integer count.

    • Close the connection.

    • table_names(db_path) — WarpCore/db.py:306-316

    • Open a connection.
    • Query table names.
    • Return them as a list.
    • Close the connection.

    Data flow¶

    Inputs¶

    The module accepts:

    • db_path: path to the SQLite database.
    • table: table name for generic helpers.
    • doc_ids: iterable of document IDs for vector deletion or upsert.
    • dim: optional embedding dimension for ensure_documents_vec.
    • schema_sql: SQL schema text for ensure_schema.

    Source data¶

    The vector logic reads from the documents table:

    • id
    • embedding

    The embedding column is treated as a BLOB containing little-endian float32 values. The code assumes:

    • len(embedding) is a multiple of 4,
    • each 4-byte group is one float,
    • the byte order is little-endian.

    Vector index data¶

    The module writes to the vector table, whose name is stored in _VEC_TABLE_NAME.

    The vector table schema is:

    • doc_id INTEGER PRIMARY KEY
    • embedding float[<dim>]

    The values inserted are serialized using sqlite_vec.serialize_float32.

    Database interactions¶

    All persistence is local SQLite. There is no IPC in this module.

    The module interacts with:

    • the main Spock SQLite database,
    • the documents table,
    • the sqlite_vec virtual table,
    • sqlite_master for table introspection.

    Return values¶

    Vector helpers return integer counts:

    • delete_documents_vec returns the number of chunks processed, not necessarily the exact number of deleted rows.
    • rebuild_documents_vec returns the number of successfully inserted vectors.
    • upsert_documents_vec returns the number of successfully updated documents.

    Generic helpers return:

    • bool for table_exists,
    • int for row_count,
    • list[str] for table_names.

    Key logic¶

    Embedding dimension inference¶

    _infer_embedding_dim(conn) is the key helper that lets the module create the vector table without hard-coding the embedding size.

    It:

    1. Selects one non-empty documents.embedding value.
    2. Reads length(embedding).
    3. Returns length(embedding) // 4.
    4. Returns None if the length is not a multiple of 4.

    This matters because sqlite_vec requires the vector dimension at table creation time. The module therefore derives the dimension from existing application data.

    Float32 BLOB assumption¶

    The module assumes embeddings are stored as raw little-endian float32 BLOBs.

    This is visible in:

    • struct.unpack("<" + "f" * (len(emb) // 4), emb)
    • sqlite_vec.serialize_float32(floats)

    This is a strong format assumption. If embeddings are stored as JSON, base64, big-endian floats, or a different dtype, the vector helpers will fail or produce incorrect vectors.

    Stale vector cleanup¶

    rebuild_documents_vec(conn) has an important edge case:

    • If no valid embedding dimension can be inferred, it drops the vector table.

    This prevents the vector index from continuing to serve stale vectors after all embeddings have been cleared. That is important for correctness: a vector index that still contains old embeddings would produce search results for documents that no longer have embeddings.

    Incremental sync versus full rebuild¶

    The module supports two update strategies:

    • rebuild_documents_vec(conn) for full resync.
    • upsert_documents_vec(conn, doc_ids) for targeted resync.

    This matters because rebuilding the entire vector table is expensive. If only a few documents changed, the upsert path avoids touching unrelated rows.

    Chunked deletion¶

    delete_documents_vec(conn, doc_ids) processes IDs in chunks of 500.

    This matters because:

    • very large IN (...) clauses can be inefficient,
    • SQLite has practical limits around variable counts,
    • chunking makes the operation more robust for large ID lists.

    Graceful degradation without sqlite_vec¶

    The module checks _SQLITE_VEC_AVAILABLE before doing vector work.

    This allows the rest of the SQLite database to continue working even if the sqlite_vec extension is missing or failed to load. The vector features simply become no-ops.

    Shadow-table awareness¶

    The presence of:

    • vec_table_names(conn)
    • vec_shadow_names(conn, name)
    • drop_vec_table(conn, name)

    indicates that the module is aware that sqlite_vec tables may have auxiliary shadow tables. This is important because dropping only the main virtual table may leave internal SQLite objects behind.

    Gotchas / maintenance notes¶

    delete_documents_vec may overcount¶

    delete_documents_vec(conn, doc_ids) — WarpCore/db.py:153-173

    The function adds len(chunk) to removed after executing the delete. It does not use cursor.rowcount.

    That means the returned value is closer to "number of IDs attempted in successful delete statements" than "number of rows actually deleted". If some doc_id values do not exist in the vector table, the count can be higher than the real number of deleted rows.

    Callers should not treat this return value as an exact row count.

    Broad exception swallowing¶

    Several vector helpers catch broad exceptions and return 0 or None:

    • ensure_documents_vec
    • rebuild_documents_vec
    • upsert_documents_vec

    This makes the module resilient, but it can hide real problems such as:

    • missing sqlite_vec extension,
    • schema mismatch,
    • invalid embedding BLOBs,
    • permission errors,
    • disk errors,
    • serialization failures.

    For debugging, callers may need to inspect the database directly because the module may not surface the underlying error.

    row_count is not parameterized for the table name¶

    row_count(db_path, table) — WarpCore/db.py:297-303

    The table name is interpolated directly into SQL:

    • SELECT COUNT(*) FROM "%s"

    This is acceptable only if table comes from trusted internal code. If table can be influenced by user input, this is a SQL injection risk.

    rebuild_documents_vec loads all embeddings into memory¶

    rebuild_documents_vec(conn) — WarpCore/db.py:209-244

    The rebuild path uses:

    • fetchall()

    on all embedded documents. For large corpora, this can consume significant memory because every embedding BLOB is loaded before insertion.

    A streaming cursor would be safer for very large databases.

    Upsert path may depend on caller transaction handling¶

    upsert_documents_vec(conn, doc_ids) — WarpCore/db.py:247-282

    The visible excerpt does not show an explicit conn.commit() after the upsert loop. The caller may need to manage the transaction boundary.

    By contrast, rebuild_documents_vec explicitly commits.

    This inconsistency can lead to surprising behavior if the caller assumes all vector helpers commit their own work.

    Mixed embedding dimensions can break the index¶

    The vector table is created with a single dimension inferred from one existing row.

    If later documents have embeddings of a different dimension, inserts into the vector table may fail. The module does not appear to validate that all embeddings have the same dimension before rebuilding or upserting.

    This is a data-integrity concern if the application can store heterogeneous embedding models in the same documents table.

    Dimension inference can silently disable vector indexing¶

    If _infer_embedding_dim(conn) returns None, vector creation or rebuild is skipped.

    This can happen when:

    • no embeddings exist,
    • the first non-empty embedding has an invalid length,
    • the length is not a multiple of 4.

    The result is a quiet no-op rather than an explicit error.

    sqlite_vec extension loading is central¶

    The vector helpers depend on _load_sqlite_vec(conn) succeeding.

    If the extension is unavailable, the module degrades gracefully, but the vector index will not be maintained. Callers should be aware that a successful return of 0 does not necessarily mean "nothing to do"; it may mean "vector support unavailable".

    Shadow-table cleanup is critical¶

    drop_vec_table(conn, name) — WarpCore/db.py:115-150

    Because sqlite_vec can create auxiliary tables, dropping the main table incorrectly can leave orphaned objects in the database. The module's vec_shadow_names helper suggests this is handled, but any future change to the drop logic should preserve shadow-table cleanup.

    Coupling to a specific embedding encoding¶

    The module is tightly coupled to:

    • BLOB storage,
    • little-endian byte order,
    • float32 values,
    • 4 bytes per dimension.

    If Spock changes its embedding storage format, this module must be updated in lockstep.

    Generic helpers open a new connection each time¶

    table_exists, row_count, and table_names each open and close their own connection.

    This is simple and safe, but it can be inefficient if called repeatedly in a loop. Higher-level code should batch these checks when possible.
